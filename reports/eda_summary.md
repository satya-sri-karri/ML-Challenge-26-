## Scale

| Source | Rows |
|---|---|
| source1 (reference) | 2,206,821 |
| source2 | 5,034,616 |
| source3 | 5,285,603 |

Total ~12.5M rows / ~1.27GB across the three source files. This is too large
for O(n²) pairwise comparison on a small machine — blocking must be
genuinely sub-quadratic (ANN/LSH-based), not just "acceptable in theory."

## Country distribution

Consistent ~60% US / ~40% India split in every source. **Training contains
only `{US, India}`**; per the problem statement the test set adds `France`,
unseen here. Nothing in this normalization module (or the profiling itself)
branches on specific country values — verified by `test_normalize_source_does_not_gate_on_country`
in `tests/test_normalization.py`.

## Ground truth

- Singleton rate: **5.58%** of source1 entities have zero true matches.
- 94.4% of source1 entities have real matches, averaging **3.67** matches
  each (max observed: 11).
- Roughly even split between source2 and source3 among matched IDs.

Implication for downstream stages: recall matters more than a naive reading
of F_0.5 might suggest, since the large majority of entities have real
matches to find, not just correctly-predicted absences.

**source1 (the reference) is clean by construction.** All observed noise —

Average field lengths are similar across sources (name ~24-25 chars,
address ~48-52 chars) — no gross truncation-by-source-file effect, though
individual truncated names do occur (see below).

## Domain-style names

~4% of both source2 and source3 business_name values are bare domains
(e.g. `aristosteel.com`, `wilfordhancock.com`). These must be cleaned
(TLD stripped) before any string-similarity feature will work on them —
handled by `text.is_domain_style()` / `text.clean_domain_name()`.

## Real noise patterns (sampled directly from matched ground-truth pairs)

These are actual matched pairs pulled from `train_ground_truth.tsv`, not
hypothetical examples:

- **Character-level typos**: `Wilblims` ↔ `Williams`, `Wanye` ↔ `Wayne`,
  `Stee1` ↔ `Steel` (digit-for-letter), `PONE` ↔ `Pune`, `Townshiip` ↔ `Township`.
- **Truncated/partial names**: `Atlantic` (alone) matched to
  `Atlantic Pinnacle Deli Inc.`; `Aristo Steel` matched to
  `Aristo Steel Private Limited`.
- **Name can be nearly unrelated while address carries the match**: a
  record named `Dréxkor` matched purely on a (typo'd) address —
  `85 Wanye Avenue, Ticonderoga Townshiip, New York` vs. the true
  `85 Wayne Avenue, Ticonderoga, NY`. **Confirms name and address similarity
  must be OR-combined downstream, never AND-gated.**
- **Address field order is not reliable**: one true match's address is
  `AZ, Fl 1st Floor, Surprise, 17437 Guthrie Street` — state first, house
  number last. **Confirms address matching must be token-set/bag-of-words
  based, not positional.**
- **Address numbers drift even in true matches**: `3928 14th Avenue` vs
  `3930 14th Avenue` vs `3928 1/2 14TH AVE`. Numbers are extracted as a
  separate field (`address_numbers`) precisely so downstream comparison can
  tolerate small deltas instead of requiring exact equality.

## What this means for normalization (this module)

1. Preserve raw values always; only add columns, never overwrite.
2. Provide both original-script and ASCII-transliterated name/address
   variants (`name_ascii`, `address_ascii`) rather than forcing one.
3. Tokenize addresses as an unordered bag, with common abbreviations
   expanded, rather than positionally parsing fixed slots.
4. Extract numeric address tokens separately from alphabetic tokens.
5. Detect and clean domain-style names explicitly (~4% of source2/3).
6. Do not "fix" typos here — that's a similarity-feature concern for
   Person C's Stage-A model, not a normalization concern.
7. Never branch on specific country values, to generalize correctly to
   France (and any other unseen country) in the test set.

## Known limitations

- `name_ascii` uses `unidecode`, a generic transliteration scheme — it is
  **not linguistically accurate** for Devanagari and other Indian scripts
  (e.g. "राम मार्केटिंग प्राइवेट लिमिटेड" → "raam maarkettiNg praaivett
  limittedd" rather than the more natural "Ram Marketing Private Limited").
  It still shares enough character n-grams with the correctly-romanized
  form to be a useful *fallback* signal, but should not be treated as a
  ground-truth transliteration.
- `name_domain_cleaned` only splits on camelCase/hyphen/underscore
  boundaries; fully concatenated lowercase domains (e.g. `heassociates.com`)
  are not word-segmented. This was a deliberate scope decision — character
  n-gram similarity features downstream still work reasonably on
  concatenated strings, and dictionary-based word segmentation was judged
  not worth the added dependency/complexity for ~4% of one source's rows.
- `strip_legal_suffix` only strips one trailing suffix per call (e.g.
  `"... Private Ltd"` → strips `"Ltd"`, leaves `"Private"` in the core).
  This is intentionally conservative to avoid eating into the real business
  name; chaining multiple strips is left to Person C if useful.
- Approximate cardinality in profiling is capped at 200,000 unique sampled
  values per column for memory safety on high-cardinality columns like
  `business_address` — see `approx_unique_is_capped` in
  `reports/eda_summary.json`.
